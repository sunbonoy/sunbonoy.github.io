# LLM Wiki 的使用体会

Andrej Karpathy 提出 LLM Wiki 概念时，核心思路是将 AI 作为"编译器"：读取一批原始文档，自动提取关键信息、建立实体关联、输出结构化 Markdown 知识库。这个概念看起来很不错，我自己也进行很多测试和使用。

## 环境搭建与执行方案

### 工具链配置
因为没有使用过Claude code和Obsidian，暂时也不想安装，使用了自己常用的工具VS Code，安装了两个核心插件：

- **Foam**：基于 Markdown 的笔记管理与知识图谱插件，利用 `[[wiki-link]]` 语法在笔记间建立双向关联，支持图谱视图可视化实体关系。
- **Cline**：AI 编程助手插件，可在对话中调用文件读写、搜索等工具，具备通过规则文件（`.clinerules`）定义任务执行流程的能力。

工作流程如下：
1. 在 VS Code 中打开一个空目录作为知识库根目录
2. Foam 自动扫描目录内的所有 `.md` 文件，解析 `[[wiki-link]]` 并生成图谱结构
3. Cline 根据预设规则读取指定目录下的源文件，按 LLM Wiki 方法论执行编译
4. 编译结果以结构化 Markdown 文件写入同一目录，Foam 自动识别新增节点并更新图谱

## 两种执行方式：规则文件和Skill

用两种方式定义了知识库的编译任务：

**方式一：规则文件（`.clinerules`）**
在项目根目录创建 `.clinerules` 文件，按优先级定义规则。具体做法是在文件末尾追加 LLM Wiki 专用的系统指令块，包括：文件读取范围、编译输出格式、实体关系提取策略、交叉引用处理规则。Cline 每次启动对话时自动加载这些规则，约束 AI 的行为边界。

**方式二：自定义 Skill 封装**
将 LLM Wiki 的编译流程封装为一个独立的 Skill（JSON 配置文件），通过指定模型、提示词模板和行为约束来实现。Skill 的优势是模块化和可复用，适合分发给多个项目使用。

**对比：规则文件表现更优。** Skill 封装在理论上更为规范和可移植，但实际运行中存在两个问题：一是 Skill 与 Cline 底层行为之间存在隐式交互，导致某些规则被静默覆盖；二是调试时排查问题链路更长。规则文件对 AI 行为的控制粒度更细、反馈回路更短，编译成功率约高出 35%。推荐初次实践的用户优先选用规则文件路线。

## 一些体会

### 上下文窗口的硬约束

- LLM Wiki 的核心机制要求 AI 在同一轮对话中先要读取规则文件并理解，再完成"读取→理解→提炼→关联→输出"的全链路操作，这意味着上下文窗口大小直接决定了一次可处理的资料量。
- 处理单篇约 1000-2000 字的技术文章并输出结构化的知识条目，需占用约 40K–60K token 的上下文。当任务扩展为 5 篇文档的交叉编译时，上下文需求的累积效应显著——模型需要同时保留所有源文档的内容摘要及正在生成的输出结构，这使得总上下文消耗突破 128K。
- 在上下文窗口低于此阈值（如 32K、64K）的模型上测试，均出现"遗忘"现象：编译进行后面时，前序内容中的概念和实体引用开始丢失，最终输出的知识图谱缺乏跨文档的一致性关联。

### Token 消耗的评估

以 5 篇中等长度技术文章（每篇约 1000-2000 中文字符）为输入，执行一次完整编译的Token消耗约 3.5M–5M token

这是一个不可忽视的数量级。这意味着：
- 免费模型的调用配额无法支撑此类任务
- 即使使用付费 API，也需要在预算层面将单次编译成本纳入考量
- 对于需要持续维护的知识库，增量编译策略（仅重新处理变动的文档）应作为默认方案

## 模型选型的选择

**Deepseek V4 和 GLM-5.1（推荐级）**
- 输出一致性：编译结果在实体识别和关系描述上高度一致，差异主要体现在措辞层面
- 复杂指令跟随能力：能够正确解析多层嵌套的执行规则，如"先提取核心概念→再识别跨文档引用→最后按层级输出"
- 推荐理由：在理解精度、执行稳定性和输出可预测性三个维度达到当前可用标准

**GLM-4.7-Flash 和 Qwen3.5-Plus（可用级，但需要人工校对）**
- 输出一致性：同输入重复运行两次，实体关系描述存在实质性差异（如同一概念被归入不同分类层级）
- 问题分析：Flash 类模型在长上下文场景下的注意力分布不稳定，导致跨文档的关联推理质量下降
- 适用场景：预算有限且愿意投入人工审核校正的场景

**本地部署 Qwen3.5-9B（Q4 量化，GGUF 格式）**
- 模型配置：基于 llama.cpp 部署，上下文窗口设置到 98K
- 执行结果：完成一篇编译可以，在执行到第 2–3 篇时出现上下文溢出导致的输出截断
- 拓展思考：若要支持此类任务，本地模型需要达到35B参数量级且上下文窗口不少于 128K，对应硬件需求至少为双卡 RTX 4090（24GB × 2）或同等算力配置，部署成本和推理延迟均需纳入考量

## 这玩意儿到底值不值得做？

这是我在测试过程中一直在想的问题。LLM Wiki 建好了，然后呢？

**它适合谁？**

- 研究人员和深度学习者。你要在一个垂直领域读大量论文或资料，需要 AI 帮你提炼、关联、形成结构化知识。这是最匹配的场景。
- 内容创作者（比如我）。累积了大量笔记和素材，需要一个能自动整理的"第二大脑"——前提是愿意为 token 买单。
- 团队知识管理。但如果团队里的资料是项目文档、会议记录这类高频变动的内容，LLM Wiki 的动态编译成本太高，不如传统 Wiki 或文档库来得实际。

**它不适合谁？**

- 预算有限的人。一次编译烧 5M token，持续维护还要反复编译。这不是给个人爱好者玩的东西，除非你刚好有免费或极便宜的 API 额度。
- 知识更新频繁的领域。每更新一点就重新编译一次？token 消耗会让你重新思考人生。这类场景更适合 RAG 或传统搜索引擎。
- 对输出确定性有极高要求的场景。大模型的幻觉问题是绕不开的。LLM Wiki 的输出可以作为"灵感"和"索引"，但不能作为唯一的知识来源。

**它真正的价值在哪？**

经过我的使用，我认为 LLM Wiki 最大的价值不是"替代你读书"，而是**帮你加速从信息到洞察的转化**。

传统做法是：读 N 篇文章 → 自己归纳 → 记笔记 → 寻找关联 → 形成理解。这个链条长，而且很依靠人的毅力和精力。

LLM Wiki 的做法是：给 AI 一堆资料 → 它帮你提取关键点、建立关联、生成结构化概览 → 你站在这个基础上做判断和深挖。

它不会让你不用读书，但它能让你读得更聪明。你从"必须读完所有资料"变成"让 AI 先给你一张地图，然后你选择深入那些关键节点"。

## 我的建议

如果你是深度学习者，在一个垂直领域持续投入，有预算上付费模型（128K+ 上下文），那 LLM Wiki 值得认真一试。工具链方面，VS Code + Foam + Cline + 规则文件是目前我验证过较为靠谱的组合，也是简单容易实现的方案。

但如果你是随便玩玩、或者想把它用在泛泛的知识收集上，我劝你先算清楚 token 账。5M token 编译一次，值不值，只有你知道。

我会继续用这个方案，看看有没有可优化的方向。
